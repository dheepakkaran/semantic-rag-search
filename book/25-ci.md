# Chapter 25 — Continuous integration

**File:** `.github/workflows/ci.yml`

## What CI is for here

Not "best practice". Two specific things:

**Catching what only breaks elsewhere.** Chapter 7's `pythonpath` bug passed
locally and would have failed in CI, because CI runs a bare `pytest` and a
laptop runs whatever is convenient. CI is a second environment, and Part VIII
showed how much a second environment is worth.

**Proving the Dockerfiles still build.** They are the least-exercised files in the
project. Nobody rebuilds an image while editing Python.

## The constraint that shapes it

Every job must be **free and offline**.

That is not frugality. A suite that spends API quota, or needs a live PostgreSQL,
is a suite that fails for reasons unrelated to the code — and a suite that fails
for unrelated reasons is one people stop reading.

Everything in Parts II–V was built with this in mind:

| Needed | How it is avoided |
|---|---|
| A language model | `LLM_PROVIDER=mock`, plus `generate()` patched in tests |
| MongoDB | `InMemoryStore` when `MONGO_URI` is unset |
| PostgreSQL | `vi.mock("../src/db.js")` |
| The Python service | `vi.mock("../src/ragClient.js")` |

So the workflow needs **no secrets at all**. Nothing to configure, nothing to
leak, nothing to expire.

## The four jobs

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  python:      # pytest
  node-api:    # typecheck + vitest
  web:         # typecheck + build
  images:      # docker build ×3
```

The first three run in parallel — they share nothing. The fourth waits:

```yaml
  images:
    needs: [python, node-api, web]
```

Building three images takes ten minutes. Doing that before knowing whether the
tests pass wastes ten minutes on every broken commit.

## What it actually costs

Real durations from one run:

```
python-service                     success   103s
node-api                           success    14s
web                                success    18s
docker images (node-api)           success    29s
docker images (web)                success    37s
docker images (python-service)     success   520s
```

The three test jobs finish in under two minutes. Then the image builds, and one
of them takes **520 seconds** — nearly nine minutes, all of it PyTorch.

That is Chapter 20's 8.88 GB, showing up as a number on a bill of time. Every
push to `main` spends nine minutes rebuilding a layer that has not changed.

Worth fixing eventually — with `cache-from: type=gha` it should reuse layers, and
the ONNX swap would remove the problem entirely. Not fixed yet, and named rather
than ignored.

## A job

```yaml
  python:
    name: python-service
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: python-service
    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: pip
          cache-dependency-path: python-service/requirements.txt

      - run: pip install -r requirements.txt pytest

      - name: Cache the embedding model
        uses: actions/cache@v4
        with:
          path: ~/.cache/huggingface
          key: hf-all-MiniLM-L6-v2

      - run: pytest -q
```

Two caches, for different reasons.

**`cache: pip`** keyed on `requirements.txt`. Unchanged dependencies mean a
restored cache instead of downloading PyTorch again.

**The Hugging Face cache** is the interesting one. Without it, every run
downloads the 90 MB model — over the network, from a third party, subject to
their rate limits. That is a build that fails for a reason that has nothing to do
with your code, which is exactly what this workflow is trying to avoid.

The key is a constant, `hf-all-MiniLM-L6-v2`, not a hash. The model never
changes; if it did, the name would.

## `pytest`, not `python -m pytest`

```yaml
      - run: pytest -q
```

Deliberately the bare command — the one that exposed Chapter 7's bug.

Running it the convenient way in CI would defeat the purpose. **CI should run
things the way production does, not the way that is comfortable**, because the
gap between those two is where this class of bug lives.

## Building images without pushing

```yaml
  images:
    needs: [python, node-api, web]
    strategy:
      matrix:
        service: [python-service, node-api, web]
    steps:
      - uses: docker/setup-buildx-action@v3

      # Build only — pushing needs registry credentials, which this repository
      # does not have. Proves the Dockerfiles work.
      - uses: docker/build-push-action@v6
        with:
          context: ./${{ matrix.service }}
          push: false
          tags: semantic-rag-search/${{ matrix.service }}:ci
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

The matrix runs three jobs from one definition, in parallel.

`push: false` is the honest position. Pushing needs registry credentials this
repository does not have, and adding them for a demo would be more secret
management than the demo is worth. Building proves the Dockerfile is valid, which
is the thing that actually rots.

> Note the tag here uses a **slash** — `semantic-rag-search/node-api`. That is the
> convention this repository would use if it pushed to a registry. It is also
> exactly the string that was wrong in the Kubernetes manifests in Chapter 24,
> where the images are local and Compose names them with a hyphen.
>
> Two different naming conventions, both correct in their own context, and the
> bug was using one where the other applied.

## Reading a green tick honestly

```
python-service                  ✅
node-api                        ✅
web                             ✅
docker images (python-service)  ✅
docker images (node-api)        ✅
docker images (web)             ✅
```

Six green ticks. What do they actually prove?

| Proven | Not proven |
|---|---|
| The Python logic works | The containers work **together** |
| TypeScript compiles | nginx routes correctly |
| The front end builds | Kubernetes accepts the manifests |
| Each Dockerfile is valid | A real database works |
| Retrieval finds the right passage | Retrieval quality, measured |

Every bug in Chapters 22 and 24 happened with CI fully green. They live in the
composition, and nothing here composes anything.

That is not a criticism of the workflow. It is the boundary of what unit tests
and build jobs can tell you, and knowing where that boundary is stops you
trusting a green tick further than it deserves.

An integration job — start Compose, ingest, ask, assert — would close part of the
gap. It is not here, and that is a gap rather than a decision.

## Why not more

No linter, no formatter, no coverage gate, no dependency scanner.

Each would catch something. Each is also a thing that fails on a Friday for a
reason unrelated to the change in front of you, and a workflow people start
ignoring is worse than a smaller one they read.

For a solo project, four jobs that run in two minutes and are always meaningful
beat twelve that are sometimes noise.

## What you should take from this chapter

| | |
|---|---|
| Why | A second environment, and the least-exercised files |
| The constraint | Free and offline, or it stops being run |
| Run it the awkward way | Bare `pytest` — that is where the bugs are |

| Build, do not push | Proves the Dockerfile without secret management |
| A green tick | Says nothing about composition — Chapters 22 and 24 were green |
